# Marketplace pre-release handoff

Version 0.3.1 is the first planned Marketplace pre-release of `MEHDIMODARRESSI.lhp-vscode`. The source repository remains `Mmodarre/lhp-vscode`. The prior VSIX used the different extension ID `Mmodarre.lhp-vscode`; it is not an in-place publisher rename. The publisher account, manual Marketplace upload and a live Marketplace installation must be verified separately. A green repository workflow or GitHub release is **not** evidence that the Marketplace listing exists.

This guide follows the [VS Code publishing guide](https://code.visualstudio.com/api/working-with-extensions/publishing-extension) and the repository's release policy. The first upload is manual. `.github/workflows/release.yml` prepares a GitHub pre-release from an exact previously tested CI artifact; it does not authenticate to or publish on the Marketplace.

## Before the first upload

1. In [Marketplace publisher management](https://marketplace.visualstudio.com/manage/publishers/), sign in with the account that will own the listing. Create or verify publisher ID **`MEHDIMODARRESSI`**. Publisher IDs are persistent Marketplace identities. Confirm the account has permission to upload under that publisher. Do not substitute the GitHub owner `Mmodarre` for the publisher ID.
2. Confirm `package.json` has `publisher: "MEHDIMODARRESSI"`, `name: "lhp-vscode"`, version `0.3.1`, the expected VS Code engine and Red Hat YAML dependency. Check the 128px-or-larger PNG icon, README screenshots, changelog, support link and Apache/third-party notices. The README's relative PNG links are rewritten to immutable source links during packaging; the four `docs/images/*.png` files must be present at the published source commit before upload. Screenshots are source-hosted, not bundled runtime assets.
3. Review the first-run copy. Python 3.11+ and the reviewed Git integration build of LHP are separate dependencies. That core commit still reports `0.9.2` metadata; Sandbox On requires the `sandbox_editor` public capability. The extension does not deploy to or execute in Databricks. Preview renders source only; confirmed generation may replace `generated/<environment>` and managed `resources/lhp`.
4. Review the identity migration text: users of the old `Mmodarre.lhp-vscode` VSIX must uninstall that extension ID before installing `MEHDIMODARRESSI.lhp-vscode`, then check project, interpreter, environment and sandbox selections. Project source and workspace files remain in place. The extension stores several selections in VS Code extension state, so those selections may reset under the new ID.

## Prepare the exact GitHub artifact

1. Merge the reviewed PR to `main`. Wait for the **Desktop extension** push CI run on that exact main commit to pass on Linux, macOS and Windows, including native VS Code integration, bridge tests, production audit and package audit. Record the CI run ID and source SHA. A PR run or a run for another commit is not a substitute.
2. Create and push tag `v0.3.1` at that same current `main` SHA. Do not move an already published tag. If source changes, run CI on the new main SHA and use a new reviewed version/tag as appropriate.
3. Dispatch **Prepare Marketplace pre-release** (`.github/workflows/release.yml`) from `main` with inputs `tag=v0.3.1` and `ci_run_id=<successful main push run ID>`. Its `release` environment must remain restricted to `main`. The workflow verifies the tag, current main commit, CI source, all three OS jobs, artifact identity, package contents, checksum and provenance before creating a GitHub **pre-release**. It cannot turn a failed or unrelated CI artifact into a release.
4. Download the GitHub pre-release assets: `lhp-vscode-0.3.1.vsix`, `lhp-vscode-0.3.1.vsix.sha256` and `lhp-vscode-0.3.1.provenance.json`. Compare the VSIX SHA256 with the sidecar and provenance. On macOS, `shasum -a 256 lhp-vscode-0.3.1.vsix` prints the digest. Retain the release URL, source SHA, CI run ID, artifact ID, byte size and checksum in the delivery record.

The release job packages nothing new and does not publish to the Marketplace. Its VSIX is the exact audited CI artifact. Do not upload a locally repackaged VSIX or the superseded 0.3.0 VSIX under version 0.3.1.

## Publish manually and verify

1. In [Marketplace publisher management](https://marketplace.visualstudio.com/manage/publishers/), select `MEHDIMODARRESSI` and upload the **exact** release VSIX as a Visual Studio Code extension. The VSIX is marked as a pre-release. Follow the portal's final review and submission flow. Do not put a PAT, Entra token or account credential in the repository, a workflow log or an issue.
2. Wait for Marketplace processing, then open the listing for `MEHDIMODARRESSI.lhp-vscode`. Check the displayed version and pre-release status, author/publisher, icon, README image URLs, support/changelog/licence links, YAML dependency and install action. The [VS Code Marketplace guide](https://code.visualstudio.com/docs/configure/extensions/extension-marketplace) explains **Install Pre-Release Version** and installation from a VSIX.
3. In an isolated desktop VS Code profile, install from the Marketplace listing and open a synthetic local LHP project. Verify the five native views, native YAML/SQL source opening, interpreter/setup guidance, Sandbox Off and On, a saved profile's selected-pipeline display, and the explicit generation warning. Check Restricted Mode before granting trust: opening trust management must end the command, and a fresh invocation after trust must work. This is a Marketplace-install test, distinct from repository CI and a VSIX smoke test.
4. Record the live listing URL, Marketplace-reported version/channel, install test OS and result, and the exact uploaded VSIX checksum. If upload or processing fails, keep publication **pending**. Do not claim success based on the GitHub pre-release alone or reuse a Marketplace version for altered bytes; prepare a new patch version and reviewed artifact.

## Later authenticated publishing

Automated Marketplace publication is **not configured** in this repository. A later tag workflow can be considered only after the publisher portal, account permissions, token exchange and actual publish API have been tested end to end. Current upstream `vsce` describes [trusted publishing with `--oidc`](https://github.com/microsoft/vscode-vsce#trusted-publishing); Microsoft also documents [Entra application identities and workload federation](https://learn.microsoft.com/en-us/azure/devops/integrate/get-started/authentication/entra?view=azure-devops), and GitHub documents [OIDC token claims](https://docs.github.com/en/actions/reference/security/oidc). These are possible approaches, not proof that either is enabled for this publisher. Keep the manual upload boundary until a scoped publisher policy and an exact-artifact publish test succeed without long-lived credentials.
