# LHP VS Code 0.3.0: sandbox and source-aware authoring

Approved implementation scope, 8 October 2026. This plan supersedes the 0.2.x sandbox limitation while preserving the shipped 0.2.1 behaviour. The target is a reviewable desktop extension and a separately isolated core change, not a claim that a sandbox run or a Databricks deployment has occurred.

## Contract and dependency sequence

1. **Core facts first.** Astra verifies the public 0.9.3 configuration and sandbox surface against the release ref, then implements only the proved gap in the isolated branch. The canonical local profile is `.lhp/profile.yaml` with `sandbox: { namespace, pipelines: [case-sensitive exact names or globs] }`; optional team policy lives in `lhp.yaml`. Core resolves patterns, policy and environment into scope, reports invalid or incomplete scope, and supplies draft validation/source preview without inventing bundle, monitoring or wheel parity. Both normal and sandbox generation replace `generated/<environment>`; sandbox generation emits profile-selected pipelines and synchronises managed `resources/lhp`. There is no namespace-specific output folder.
2. **Typed host state.** Sol host projects canonical core results into `SandboxViewState` on bootstrap/snapshot and a `sandbox` update when a display or mode change does not require a graph refresh. Agreed state includes `mode`, fixed `profilePath`, `profileExists`, `profileSource`, `namespace`, `patterns`, `selectedPipelines`, `totalPipelines`, `allowedEnvironments`, `environment`, `display`, `valid/error`, `stale`, `scopeComplete`, `previewParity` and known `generatedOutputScope`. Initial mode is Off. The host persists mode/display per project in workspace state and publishes the same choice to the native view and GUI; neither surface infers it separately. Unknown or dynamically resolved facts remain explicitly unknown. Host methods are `setSandboxMode`, `configureSandboxProfile`, `setPipelineDisplay` and `showSandboxScope`; every request is allowlisted, trusted where it can write/run, project/revision checked, and follows native TextDocument/WorkspaceEdit rules.
3. **GUI and native tree consume the same facts.** The webview does not infer sandbox selection from graph data. `Show all` changes display only; it cannot change generation, validation or preview scope. The native tree remains canonical for physical files and displays every actual source directly under each consuming flowgroup, including shared files under multiple consumers. Stable source references, known use counts and completeness flags are exposed by Sol host. Counts cover the whole known project, not just the current sandbox display. Profile changes refresh both surfaces without stale cross-project state.
4. **Verification then packaging.** Owner tests run on their respective contracts before full integration. Root independently checks the user workflows, desktop matrix, production dependency audit and VSIX contents before a coordinated commit/push. No Marketplace publication or merge is implied by this plan.

## Webview contract details

- GUI sends `{ type: 'setSandboxMode', mode: 'off' | 'on' }`, `{ type: 'configureSandboxProfile' }`, `{ type: 'setPipelineDisplay', display: 'selected' | 'all' }` and `{ type: 'showSandboxScope' }`. These are intent messages, never profile content or arbitrary file paths.
- `SandboxViewState` is host-owned on `bootstrap`, `snapshot` and a dedicated `sandbox` update. The GUI validates incoming shape and project/revision identity before applying it, clears it on project switch and uses the host's `selectedPipelines` for the default filter. A display-only preference must not be used as an operation argument.
- For resource usages, the host supplies stable exact source references with known counts and a completeness bit. GUI tooltips and `Show usages` render these facts, including an explicit “known uses” qualifier when discovery is incomplete.
- All structured edits remain document-version-checked native WorkspaceEdits. A graph edge, shared source, template parameter or generated artifact never becomes a private editable copy in React state.

## Explicit limits and open proof points

- Core public APIs, profile draft handling and generation target semantics must be proved against the new isolated core branch before any UI assertion is finalized. Sol GUI may render placeholders in demo/tests during development, but release copy must be backed by host facts.
- Source preview is limited to what the core returns. Bundle synchronization, monitoring finalization, wheel artifacts and remote execution are not represented as previewed or completed.
- Dynamic template values and consumers may not be statically knowable. Show definition/instance provenance and uncertainty instead of a guessed effective value or exhaustive count.
- File Icon Themes and Product Icon Themes are user choices. SQL/Python file symbols will follow the selected file theme, while custom semantic SVGs require separate dark/light/high-contrast review.
