# Research and product decisions

Research was performed against primary vendor documentation and the LHP release source on 8 October 2026. The implementation started from LHP `release/V0.9.3` commit `2362454069f91241ec5927a0ae88a1e3df88ad22`; the reviewed integration API is pinned to `98d285ab8a7606867abb5708f2715ebe31a9befc`. This document records evidence and resulting decisions, not claims of feature parity with the products below. Product packaging and entitlements can change; this comparison does not promise paid/free availability.

## What comparable products establish

| Primary source | Evidence and useful precedent | Decision for LHP |
| --- | --- | --- |
| [Official dbt extension features](https://docs.getdbt.com/docs/dbt-extension-features), [about the extension](https://docs.getdbt.com/docs/about-dbt-extension) | Semantic SQL/YAML authoring, project context, lineage and source/compiled navigation are integrated into a development workflow. The official dbt/Fusion extension is distinct from Altimate's dbt Power User. Language coverage, supported engines and remote-development limits must be read precisely. | Make generated Python and resolved dependencies visible beside declarative source. Do not claim dbt-like bidirectional source mapping when LHP has no compiler source map. Ship file-level source navigation and explicit source-only preview. |
| [Official Databricks bundle workflow](https://docs.databricks.com/aws/en/dev-tools/vscode-ext/bundles) | Bundle configuration, target selection, validation, deploy/run and Problems integration belong to the Databricks extension's workspace-aware execution surface. | Generate LHP source and bundle resources locally, then open `databricks.yml` and hand off. Reimplementing authentication, cluster selection, execution and deployment would duplicate a maintained vendor tool and increase operational risk. |
| [Red Hat YAML repository](https://github.com/redhat-developer/vscode-yaml), [contributor API](https://github.com/redhat-developer/vscode-yaml/wiki/Extension-API), [current API source](https://github.com/redhat-developer/vscode-yaml/blob/main/src/schema-extension-api.ts) | JSON Schema validation, completion and hover already exist. Extensions can synchronously select schema URIs and provide schema content. The current API registers a scheme once; it has no contributor disposal API. | Depend on Red Hat YAML and contribute runtime-matched schemas through one mutable registry. Add LHP semantic references and canonical diagnostics. Do not write another YAML language server or silently replace users' settings. |
| [HashiCorp Terraform language server features](https://github.com/hashicorp/terraform-ls/blob/main/docs/features.md) | Different validation layers and semantic completion/navigation are explicit. A schema-valid document is not proof that resolved templates, references and dependencies are valid. Avoid an unsafe broad rename operation masquerading as semantic refactoring. |
| [SQLMesh VS Code guide](https://sqlmesh.readthedocs.io/en/latest/guides/vscode/) | Interpreter/environment selection and project-aware SQL model development are essential in a Python-based engine. Preview and runtime semantics have environment/engine boundaries. | Treat interpreter, LHP API capability and environment as first-class context. Include unsaved text safely in a mirror; keep runtime execution separate. Do not make a Python installation error look like invalid pipeline YAML. |
| [Kestra VS Code documentation](https://kestra.io/docs/version-control-cicd/vscode) | YAML authoring can coexist with diagrams and schema support. Its schema/runtime relationship is a useful precedent for version-matched DSL assistance. | Balance native YAML with an approachable graph/form surface. | [Dagster dg CLI utilities](https://dagster.io/docs/api/clis/dg-cli/dg-utils) | Generated configuration schemas and project tooling connect runtime-owned component contracts to editors. | Derive schemas and catalogue/help from the selected installed LHP API. Avoid a second hand-maintained list of supported action subtypes in TypeScript. |

The common lesson is context and semantic feedback, not maximum feature count. A graph without the engine's dependency analysis is a misleading picture. A form that saves elsewhere becomes a merge problem. A preview that silently writes output is a deployment risk. A setup screen that creates a project which cannot pass its first generation is incomplete onboarding.

## LHP source findings

LHP already had a substantial public facade, project bootstrap, template/preset inspection, generation planning, canonical validation and dataset dependency analysis. Its existing web GUI supplied useful interaction precedent, but was not an appropriate extension architecture: desktop VS Code owns native documents, editors, search, source control and undo. Embedding the whole existing server/Monaco stack would duplicate those facilities and introduce a second save model.

The public facade follows frozen DTO and event-stream rules. The extension therefore uses new standalone public editor functions rather than adding an eighth facade or importing internal resolvers. Long validation and preview operations preserve `Iterator[LHPEvent]`; the bridge emits ordered NDJSON events and returns the terminal DTO.

Inspection needed exact provenance. A source filename alone cannot identify an action in a multi-document YAML stream or a `flowgroups` array. Generated template and blueprint actions also need separate invocation and definition locations. The integration API supplies document index, key/index path and UTF-16 source spans, raw invocation data and resolved actions. Blueprint parameter forms edit invocation YAML; action definitions remain shared. Synthetic monitoring flowgroups are visibly generated and navigate to project configuration.

The dependency API already knows about SQL/Python-derived dependencies. The first adapter draft reconstructed edges from source/target strings; review rejected that approximation. The implementation now consumes the canonical graph directly with pipeline-qualified identities. String matching may label a canonical edge and determine whether a direct input can be edited; it never invents an edge.

Generation required careful boundary checks. A filtered generation can replace the entire environment output tree. The extension therefore offers only explicit full-project generation. Passing `output_dir=None` to the public generation facade is a dry run, despite returning a successful response; the bridge sets the CLI-equivalent `generated/<environment>` path. Bundle policy uses the public `should_enable_bundle_support` function. Test hook emission stays opt-in like the CLI.

Generation planning renders source in isolation but excludes bundle finalisation, monitoring finalisation and sandbox parity. Wheel output is binary and cannot be treated as UTF-8 preview content. The UI labels preview as source-only, rejects unsupported wheel preview, and opens read-only generated files that expire when inputs change. No bidirectional line map or deployment-plan equivalence is claimed.

Runtime selection must be capability-based: the release branch's package metadata remains `0.9.2` even though the editor integration targets unreleased 0.9.3. A simple `>=0.9.3` check would reject the authorised build; accepting all PyPI 0.9.2 installations would fail later. Guided installation pins the reviewed source SHA and verifies required public APIs.

Real lifecycle testing found two onboarding details that mocks would miss. The bronze scaffold must split a fully qualified table into catalogue/schema/table fields. Also, normal project bootstrap leaves example configuration as `.tmpl` files; enabling a bundle does not produce an active pipeline config. New-project bundle setup therefore asks for explicit catalogue/schema defaults and creates the active configuration that generation requires. Existing projects retain an explicit configuration selection.

## Novice and expert workflows

A novice opens a trusted folder, selects Python or creates a virtual environment, and installs the pinned integration build. Project creation can include a Databricks bundle with explicit default catalogue/schema. The designer's files-to-bronze form asks for a flowgroup, pipeline, landing path, file format and fully qualified target table. It creates native YAML, shows the two actions, lets the user inspect generated source, validates the resolved project, and performs full generation only after an explicit save/scope confirmation. Deployment remains a named handoff to Databricks.

An expert opens an existing multi-project workspace, selects the correct LHP root, interpreter, environment and optional pipeline configuration. YAML remains the primary editor. Runtime schemas, completion, hover and definition links reduce lookup effort; canonical Problems expose resolution failures. The graph drills from pipelines to flowgroups and actions, including code-derived dependencies. Selecting an action reveals native YAML; related SQL/Python/schema/expectations files open in normal editors. Forms preserve unknown keys and submit version-checked edits. Undo/redo works across visual and textual changes.

Both workflows use template/blueprint catalogues from the actual project, including nested template references and parameter metadata. Generated actions show why they are read-only and where to edit their instance or shared definition. Source errors retain the last valid graph with a stale marker; graph edits are disabled until the source is valid, while native recovery remains available.

## Scope boundaries

The user requested all authoring graph operations, native action-file editing, guided creation, environment selection, validation, preview, generation and Databricks handoff in the first release. They are acceptance criteria, not an optional future backlog. Unsupported code-derived connect/disconnect operations are presented honestly with native-source navigation because rewriting arbitrary SQL/Python is not a mechanical graph edit.

The user explicitly chose desktop delivery, VSIX distribution and no Marketplace publication. Remote/browser support and cloud execution are outside this delivery. AI generation, warehouse query execution, row previews, live runtime debugging, broad semantic rename and bidirectional compiled line mapping were research comparisons, not accepted implementation requirements. They should only be added when their correctness contract and user value are clear.
